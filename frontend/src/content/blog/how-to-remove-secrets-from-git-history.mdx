## Why Deleting the File Isn't Enough

If you commit an API key, then delete the file and commit again, the key is **still in your history**. Anyone can run `git log -p` or check out an old commit and read it. On a public repo, automated bots scrape new commits within minutes — assume a leaked key is compromised the moment it's pushed.

Removing a secret properly takes two separate actions: **rotate** the credential (so the leaked value is useless) and **rewrite history** (so the value is gone from the repo). Do them in that order.

## Step 1: Rotate the Secret First

Before touching Git, invalidate the leaked credential at its source:

- **API keys / tokens:** revoke and regenerate in the provider's dashboard (AWS, Stripe, GitHub, etc.).
- **Passwords:** change them everywhere they were used.
- **SSH/signing keys:** generate a new pair and remove the old public key from all servers.

This matters because history rewriting is never instant or guaranteed — forks, clones, and caches may still hold the old value. A rotated secret is harmless no matter where the old value ends up.

## Step 2: Find Every Place It Leaked

A secret may appear in more files and commits than you remember — a `.env`, a config snippet in a README, a hardcoded fallback in code. Search the full history:

```bash
# Search all of history for a known string
git log -p -S "AKIA" --all          # AWS-style key prefix
git grep "password" $(git rev-list --all)
```

Manual grep misses patterns you don't think to search for. GitTool's [secrets scanner](/tools/secrets-scanner) audits your entire repository for hundreds of credential patterns — API keys, private keys, tokens, connection strings — so you scrub *everything*, not just the one key you noticed.

## Step 3: Rewrite History with git filter-repo

The modern, recommended tool is [`git filter-repo`](https://github.com/newren/git-filter-repo) (the old `filter-branch` is slow and error-prone). Install it, then replace the secret across all history:

```bash
# Create a replacements file
echo 'AKIAIOSFODNN7EXAMPLE==>REMOVED' > replacements.txt

# Rewrite every commit, replacing the secret
git filter-repo --replace-text replacements.txt
```

To remove an entire file (like a committed `.env`) from all history:

```bash
git filter-repo --path .env --invert-paths
```

For repos hosted on GitHub, the [BFG Repo-Cleaner](https://rtyley.github.io/bfg-repo-cleaner/) is a faster alternative for the common cases:

```bash
bfg --delete-files .env
bfg --replace-text replacements.txt
git reflog expire --expire=now --all && git gc --prune=now --aggressive
```

## Step 4: Force-Push and Notify Your Team

History rewriting changes every commit hash after the affected commit, so you must force-push:

```bash
git push --force --all
git push --force --tags
```

This is one of the rare times a force-push is correct. **Tell your team immediately** — everyone must re-clone or carefully rebase, because their old clones still contain the secret and the old history. Also ask GitHub support to purge cached views of the old commits if the repo was public.

## Preventing the Next Leak

Cleaning history is painful enough that prevention is worth real effort:

- Add `.env`, `*.pem`, and credential files to `.gitignore` **before** the first commit.
- Install a `pre-commit` hook that scans staged changes for secrets (see our [Git hooks guide](/blog/git-hooks-practical-guide)).
- Run a repository secret scan in CI so a leak fails the build instead of reaching production.

GitTool's [security tools](/tools/secrets-scanner) bring detection into your normal workflow, so the cheapest time to catch a secret — before it's ever committed — is also the default.
